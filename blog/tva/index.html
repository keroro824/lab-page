TVA: AI Agents Prove Triton Kernels Correct

Tests check the shapes you think of. A proof covers every launch. TVA is a Lean 4 library and an agent sandbox in which AI agents prove that the Triton kernels behind LLM serving, from SGLang, vLLM and flash-linear-attention, are correct on every launch they cover: no fault, no race, nothing written outside their outputs, and every output within a stated bound of the exact answer.

Zhuoming Chen · InfiniAI Lab, Carnegie Mellon University · November 2026
Code on GitHub ↗

The inference stack is now a target

The last few months made one thing plain: the software that serves AI models is being attacked like any other high-value infrastructure.

  • Inference providers. Fireworks AI disclosed unauthorized use of internal credentials in early October 2026 and a second intrusion through a third-party cloud provider later that month; a November update widened the scope to account data and, for some customers, secrets, datasets and incomplete model weights (Crypto Briefing, Dr. Web).
  • Serving engines. SGLang received a CVSS 9.8 remote-code-execution report, CVE-2026-5760, in which a crafted chat template inside a GGUF model file runs code on the server, after two earlier critical deserialization flaws (The Hacker News, CSA).
  • The supply chain. In the PHP ecosystem, a malicious intercom-php release and a compromise of the Laravel-Lang packages pushed credential stealers and backdoors into widely installed libraries, through the projects' own release channels (Cloudsmith, The Hacker News).

None of these incidents went through a GPU kernel. But they share a pattern: attackers go where code is trusted, changes fast, and is too large for anyone to re-read. GPU kernels fit that description better than almost anything else in an LLM stack. vLLM and SGLang together contain about 1,800 @triton.jit functions, new ones arrive with every model architecture, and more and more of them are written by AI agents. A kernel runs with access to the whole GPU memory: the weights, and the KV caches of every request in the batch. And its failures are silent. An int32 offset that wraps only past a few million tokens, a mask that is off by one row, or a race between programs does not crash anything; it returns a plausible wrong answer, or reads a byte that belongs to someone else. Research has also started to treat the numerical layer itself as an attack surface, with backdoors that trigger only under particular compiler optimizations or hardware (1, 2).

Testing samples a few shapes and a few inputs. Code review does not scale to the rate at which kernels change. What does scale is a proof that a machine checks: a statement that holds for every launch the host can make, checked by a small trusted kernel rather than by whoever reviews the pull request. Writing such proofs by hand is far too expensive, which is why nobody does it for production kernels. Our bet is that AI agents can now write them.

What TVA is

TVA has three parts.

  1. A Lean 4 semantics of Triton. About 8,300 lines of Lean define what a Triton program means: tensors, the tl.* operations, masked loads and stores, atomics, and a launch as programs interleaving over a byte-addressed memory. Floating-point values are exact IEEE bit patterns (fp32, fp16, bf16, fp8 formats, mxfp8 with e8m0 scales) with exact rounding; integers are fixed-width and wrap. Operations whose result the hardware leaves open, such as tl.exp, the accumulation order inside tl.dot, or float atomics, return any value allowed by a device fact, and each device fact is backed by our own measurements on an H200.
  2. Fixed claims about real kernels. A claim transcribes a kernel line by line into that vocabulary and states which launches it covers and what every covered launch must leave in memory. Claims are written once, by hand, and pinned by their SHA-256.
  3. A proof kit and a sandbox for agents. About 16,000 lines of proved lemmas (memory access patterns, loops, integer widths, floating-point error, tl.dot accumulation, online softmax, decayed recurrences, scans, shared atomics) let a prover walk a kernel one program at a time. A container gives an agent the claim, the library and the docs, and one tool that grades its proof.

What a claim says

Every claim has the same shape. Inst is everything the host chooses (shapes, scalars, buffers), ok says which choices are covered, and Post says what the final memory must satisfy: 

def Claim.Holds (c : Claim) : Prop :=
  ∀ P, Device P →                    -- every platform with the H200's device facts
  ∀ d, c.ok d →                      -- every covered launch: shapes stay symbolic
  ∀ init, c.Pre d init →             -- every initial memory, including the data
    Correct (c.kernel d) (c.launch d) init (c.Post d init)
-- Correct: no undefined behaviour, no race between programs, and every way the launch can end
-- is a normal end (no fault, no hang) whose final memory satisfies Post.

Here is the model of Triton's vector-addition tutorial. Each line reads one line of the source, and the comments say how: 

def add_kernel (x_ptr y_ptr output_ptr : Ptr .f32) (n_elements : I32) (BLOCK_SIZE : Nat) : Kernel where
  body ctx := do
    let pid := tl.program_id ctx 0
    -- `pid * BLOCK_SIZE` is computed in int32, and wraps
    let block_start := pid * (IntV.ofNat BLOCK_SIZE : I32)
    let offsets := block_start + tl.arange 0 BLOCK_SIZE
    let mask := offsets.ltS n_elements
    let x ← tl.load (x_ptr + offsets) (some mask)
    let y ← tl.load (y_ptr + offsets) (some mask)
    let output ← tl.add x y
    tl.store (output_ptr + offsets) output (some mask)

Its Post says that element j < n of the output is the IEEE sum of the inputs' elements j, and that every other byte of memory is unchanged. That last clause is in every claim. A proved kernel writes only its outputs.

For production kernels the interesting part is the conditions. SGLang's 50-line vocabulary embedding lookup needs eleven of them: the ids are int32 or int64, BLOCK_H is a power of two, the int32 column index cannot wrap, the grid fits CUDA's limits, every vocabulary index of the tensor-parallel shard fits in int64, and the output shares no byte with the inputs. None of these is written in the kernel's source. A claim makes every one of them explicit, so a reader can check them against the code that launches the kernel. For floating-point kernels, Post bounds the error against the exact real-number result with a tolerance that is derived from the device facts and stays meaningful at the largest covered size.

What you trust

The list is short and lives in one file: Lean and Mathlib; that the claim's model is the kernel, which a reader checks line by line; that Triton 3.8.0 compiles the kernel as the model says, outside a published list of 56 excluded features and situations, among them known miscompiles; and the device facts, each with its measurements. Everything else, including the 16,000 lines of proof kit and every agent-written proof, is checked by Lean.

Agents prove, a machine grades

Because claims are fixed, nobody needs to judge an agent's proof. An agent gets one claim in a container, as a task in the Harbor framework: the claim's files, the built library with its documentation, and one worked example. It writes theorem main : claim.Holds in Lean, often split into many modules, and builds as often as it likes. A grader in a separate container then runs five checks:

  1. the claim file is byte-for-byte the pinned one;
  2. the proof uses no escape hatch: no sorry, axiom, native_decide, implemented_by, meta code, local instances or foreign imports;
  3. everything builds from scratch;
  4. main has exactly the type claim.Holds and depends only on Lean's three standard axioms;
  5. Lean's kernel re-checks every declaration of the claim and of the proof from the compiled files.

The answer is a reward of 1 or 0. Nothing in it depends on trusting the agent. Each claim also keeps a reference proof, and the sandbox never shows it to an agent: a task copies only the claim's own files, through an allow-list that also refuses any file whose content matches a reference proof.

Results: all 41 claims proved by agents

We wrote fixed claims for 41 kernels. Fourteen are Triton tutorial and library kernels: vector addition, softmax, layer norm, fp16, fp8 and mxfp8 GEMMs, persistent and TMA GEMMs, stream-K with atomics, FlashAttention forward and backward, and paged attention. Twenty-seven are production kernels: 12 from SGLang, 7 from vLLM and 8 from flash-linear-attention, covering extend and prefill attention over paged and variable-length batches, fused MoE, LoRA, int8 scaled GEMMs, speculative-decoding rejection sampling, KV-cache writes, Mamba-2 SSD and gated DeltaNet chunked recurrences.

Every one of the 41 claims now has a complete proof written by AI agents and accepted by the grader in a fresh container: 40 of them by Claude Sonnet 5.5 agents, plus the vector-addition worked example. The hardest took several agent sessions, each handing a written plan to the next.

Proof size tracks what makes a kernel hard to reason about rather than its length. Elementwise and gather kernels are short. GEMMs need the error of a tl.dot accumulation over the K loop. Attention kernels need an online-softmax invariant whose error bound survives every rescaling, and the chunked recurrences of linear attention need a state invariant carried across chunks with decays. SGLang's extend attention, with its paged KV cache, tree masks for speculative decoding and sliding windows, needed 49 modules.

How TVA compares

Formal verification of GPU kernels has moved fast this year. The systems closest to ours verify machine-learning kernels at the PTX level or against a reference program:

Volta checks that an optimized kernel is equivalent to a reference by symbolic execution, with thread counts, tensor sizes, pointer targets and branch conditions known statically, and compares expressions over the reals; its open implementation, ptx_verifier, extracts Lean propositions for a fixed size. SentryWard verifies synchronization, race freedom and equivalence for warp-specialized Hopper and Blackwell kernels at fixed sizes, excluding addresses and branches that depend on loaded values. Formalizing PTX in Lean models every execution of hand-written PTX against the PTX memory model, including asynchronous copies and tensor cores, with LLMs writing the proofs. Earlier tools such as GPUVerify and Faial prove race freedom only, and recent agent systems for CUDA, such as ProofWright and Browne et al., target elementwise kernels or a CUDA subset.

TVA makes a different trade. It works one level higher, on Triton programs, and trusts the Triton compiler with one stated rule. In exchange it covers what production serving kernels actually do: shapes known only at run time, addresses read from memory (page tables, expert maps, sequence offsets), integer arithmetic that can wrap, and floating-point results that are not equal to the exact answer and must be bounded honestly. A real-number equivalence proof says nothing about how far a bf16 attention output may be from exact attention at a long context. A TVA claim states that bound, and the proof establishes it.

Limits

  • The Triton compiler is trusted outside the exclusion list, and claims cover one stack: Triton 3.8.0 on the H200.
  • Claims are written by hand, and a reader must still check that a model transcribes its source. The fixed shape of a claim, a line-by-line model with comments, keeps that check local.
  • A proof guarantees what the claim states. Each claim says which launches it leaves out and why, and some real modes are left out, for example in-kernel TMA descriptors.
  • Proofs are long and agent time is not free. Making agents cheaper and more reliable at this is the next step.

What's next

The 41 claims and their checker are, in effect, a benchmark: each task is one kernel and one fixed claim, and success is a binary machine check that cannot be gamed by weakening the specification. We are using it to measure how well different models prove kernels, and we are working toward the case that matters most: when a kernel is wrong, an agent should come back with a concrete launch that breaks it rather than with nothing. The library, the claims and the sandbox are open source at github.com/Infini-AI-Lab/TVA.

In one sentence: TVA turns "this kernel passed our tests" into "Lean checked that this kernel is correct on every launch its host can make", and lets AI agents do the proving.
